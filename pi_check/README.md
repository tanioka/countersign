# pi_check — Raspberry Pi 実機との食い違い洗い出し

`--real-dev` の生成物(I2C・SPI・GPIO・時計・UART・作業メモリ)を実機で走らせ、疑似カーネル(`fake_kernel.py`)の予想と突き合わせる一式。

1. この箱で `python3 build.py`(clang と ld.lld が要る)→ `bin/` に AArch64 の静的 ELF。`python3 make_expected.py` → `expected.json`(疑似カーネルの予想)。どちらも作ってあるので、Pi に持っていくだけでよい。
2. Pi(64 ビットの Raspberry Pi OS)に、この `pi_check/` を丸ごと置き、`python3 run_on_pi.py`。`report.md` と `report.json`(と `trace/`)ができる。それを返してほしい。
3. 準備: I2C・SPI を raspi-config で有効に。ユーザーが `gpio`・`i2c`・`spi` グループに入っていること。GPIO26(37 番ピン)に何もつながない。SPI のループバックを見るなら GPIO10 と GPIO9 を線 1 本でつなぐ。AHT25 があれば I2C につなぐ。

何もつながなくても動くのは: t_map・t_clock・t_uart・t_gpio_*・t_i2c_probe/nobus・t_spi_ret・t_alarm・t_net_*(ネットワークはこの機の中のループバックだけを使う。外へは出ない)。
実機では未実行。判定の「一致/許容/食い違い」の基準は、疑似カーネルの予想と、私が見込んだ実機の振る舞い(PROBE の失敗番号など)から決めたもの。

## 追加: 入力(0x9300000。/dev/input/event*)

- `t_input_idle`: 何も触らずに 件数・MX・MY・ボタン を出す(参考)。開けた event が無ければ全部 0。
- `t_input_live`: 3 秒のあいだ 20 ms ごとに集めて、出来事を「種類 符号」で出し、最後に件数を出す(参考)。**走らせている間にキーを押す・マウスを動かす・クリックすると増える**(ssh 越しなら、Pi につないだキーボード・マウスを触る)。
  種類: 1 キー押下 2 キー離す 3 マウス移動 4 マウス押下 5 マウス離す。符号: a は 97、Enter 13、Esc 27、Space 32、左 28 右 29 上 30 下 31。
- 要る権限: `input` グループ(`/dev/input/event*`)。ユーザーが入っていれば開ける(`id` の groups に input)。
- 実機の確かめ方: `python3 run_on_pi.py` の前後ではなく、`bin/t_input_live` を直接走らせて、その間にキーを押してみるのが早い(strace の trace/t_input_live.txt に read の中身も残る)。

## 追加: 描画(0x9100000。/dev/fb0)と音(0x9800000。aplay)

- `t_gfx_fb`: 赤で塗って緑の長方形を描き PRESENT。FRAME・STATUS を出す(参考)。**画面に出るのは tty のコンソールだけ**(X・Wayland の下では出ない)。要 `video` グループ。開けなければ stderr に `ERR` を 1 度出して以後の PRESENT を捨てる。

## 追加(第109段): 投機(`--par-spec`)を測る 4 本(`t_spec_*`)
`|`・`&`・枝(`cond : v`)の右・値を、左・条件を調べる間に別のスレッドで先に走らせる(必ず終わると言える関数だけ。罠は巻き戻して捨てる)。**直列(`_s`)・`--par=4`(`_p4`、投機なし)・`--par-spec`(`_spec`、4 本)**を同じ機械で走らせ、答えが同じか・どれだけ速いかを測る。

- **追記(再測定)**: 投機の比べ(`t_spec_*`)は、変種を **1 周ずつ順に**走らせる(以前は変種ごとに 3 回まとめて走らせていた)方式に変えた。熱や時間の流れの偏りが特定の変種に乗らない。周回数は環境変数 `SPEC_REPEAT`(既定 5。例: `SPEC_REPEAT=9 python3 run_on_pi.py`)。備考に「N 周の最短・中央値・最大」を、`report.json` に `all_seconds`(全周の時間)を書く。倍率は最短どうしの比。最短と中央値が離れている行は、揺れが大きいので比べを割り引いてほしい。
- **追記(周回方式を並列・最適化にも)**: `t_par_*`(並列)と `t_opt_*`(最適化)の比べも、変種を 1 周ずつ順に走らせる方式にした(`t_spec_*` と同じ)。周回数は環境変数 `PAR_REPEAT`・`OPT_REPEAT`・`SPEC_REPEAT`(既定はどれも 5。時間を縮めたいときは `PAR_REPEAT=3 OPT_REPEAT=3 SPEC_REPEAT=3 python3 run_on_pi.py`)。全体の所要時間は従来の約 1.7 倍。最短と中央値が離れている行は、その間の環境が揺れていたので比べを割り引くこと。
- **追記(二つの山の調べ)**: 同じバイナリの周ごとの時間が約 1.7 倍の二つの山に分かれる現象(`fib4_p4` など)を調べるため、各周の CPU 時間(子の user+sys)と文脈切り替え(自発・強制)も記録する。`report.json` の `laps` は周ごとの `[wall, CPU, 自発切替, 強制切替]`。最大が最短の 1.3 倍を超える行は、備考に「【山あり】」で最短の周と最長の周の CPU/wall と切替を並べる。見方: 遅い周で CPU/wall が下がる(例: 3.9→2.2)= コアを使い切れていない(4 本のうち数本が同じコアに載った、待ちが長い)。CPU 時間が増えて CPU/wall は同じ = 空回り(待ちの自旋)。CPU 時間も wall もそのまま増える = 1 本あたりが遅い(周波数・取り合い)。周回数が少ないと山が見えないので `PAR_REPEAT=9` などで増やしてよい。
- **追記(`_p3` を並列の比べに)**: `t_par_*` の 7 本に `--par=3` の変種(`_p3`、新しく 7 個)を足した(bin は計 118 個)。二つの山(同じバイナリの周ごとの時間が約 1.7 倍に分かれる)が、4 コアに 4 本を載せたときだけ出るかを見る。見る点: (1) `_p4` の備考の「`_p3` の平均 x 秒に対し平均 y 秒(`_p3` の z 倍)」。山があっても `_p4` の平均が `_p3` より速ければ 4 本のほうが得、`_p3` のほうが速ければ 4 コアに 4 本は損(1 コア空けたほうがよい)。(2) `_p3` 自身に山(最大が最短の 1.3 倍超)が出ないか。出なければ、山は 4 本が 4 コアを占める場合の効果という仮説に合う。(3) 備考に平均も出す。

## 軽さの境を変えた並列版 (_p4l0 / _p4l100 / _p4l20k / _p4l200k)
`--par=4` の「軽い仕事は直列にする」判定(`--par-light=N`、既定 1000 クロック)を変えた版。
3 回続けて軽いと呼び出し位置が永久に直列になる仕組みが、`_p4` の二峰(速い/遅い周回)の原因と推定している(IMPLEMENTATION_NOTES 続き 19)。
`_p4l0` は軽さ判定なし。`_p4` の平均・最大・CPU/壁と比べ、遅い周回が消えるか、細かい呼び出しの多い題材で遅くならないかを見る。

## スレッドごとの切替の診断 (*_threads 行)
t_par_fib・fib4 の `_p4`/`_p4l0` を走らせながら /proc/<pid>/task/*/status を 5 ms ごとに読み、スレッドごとの自発的/強制の切替の最後の値を出す(先頭が主スレッド)。`_p4l0` の遅い周の切替(4000 回超)がどのスレッドで起きるかを見るため。strace は使わない。

## join の見回りの版 (_p4s300 / _p4l0s300 / _p4l0s3000)
`--par-spin=N`: join が走行中の仕事を待つとき、futex で眠る前に N 回状態を見に行く(既定 0)。`_p4l0`(軽さ判定なし)で自発的切替が数千回に増える原因(軽い仕事のたびに眠る往復)を減らす試み。`_p4l0` と比べて、切替・壁時計・CPU/壁がどう変わるかを見る。`*_threads` 行は `_p4l0s300` も出す。

(追記)`*_threads` 行はスレッドごとの CPU 時間(ms、schedstat)も出す。fib・fib4 の `_p4` は 8 周。遅い周で 1 本だけ長く走っているかを見る。

## 軽さを積みの深さで覚える版 (_p4r / _p4rl100 / _p4rl20k)
`--par-relight`: 「軽い」と測った呼び出し位置を永久に直列にする代わりに、スレッドごとに「軽かった枠の深さ」を覚え、それより浅い枠でだけ仕事を出す。`_p4` の遅い周(仕事の分け方が粗いまま固まる)を無くす試み。`_p4` と比べて、遅い周が消えるか・合計 CPU が増えないかを見る。`*_threads` 行は `_p4`・`_p4r`・`_p4l0`。

## 並列の版の整理(深さ方式が既定)
`--par=N` の既定が変わった: 軽さを「スレッドごとの積みの深さ」で覚える方式(境 100)。並列の題材は `_s`・`_p2`・`_p3`・`_p4`(新しい既定)・`_p4site`(前の既定 = `--par-site-light`、位置ごとの数え・境 1000)・`_p4l1000`(深さ方式で境 1000)・`_p4l0`(軽さ判定なし)。上の節に出てくる `_p4r`・`_p4rl100`・`_p4s300`・`_p4l0s300`・`_p4l100`・`_p4l20k`・`_p4l200k` などは外した(結果は IMPLEMENTATION_NOTES 第109段 続き 20〜31)。`*_threads` 行は fib・fib4 の `_p4` と `_p4site`。

## 特殊化の題材 (src_hof/、t_hof_*)
関数を渡す呼び出し(`$f` を渡して `@f x` で呼ぶ)が、渡された関数ごとの実体になっているかを実機で見る。高階関数の版(`_hof`)と、同じ計算を手で特殊化した版(`_dir`)を並べ、答えと時間を比べる。周回数は環境変数 `HOF_REPEAT`(既定 5)。

| 題材 | 中身 | 答え |
|---|---|---|
| t_hof_rep | `rep $step 100000000 0`(関数を 1 億回当てる輪) | 300000000 |
| t_hof_fold | `fold $add 0 xs` を 3000000 回(括りの残り `[h ~t]` で器を畳む) | 165000000 |
| t_hof_map | `fold $[a b ? a + b] 0 (map $[* 2] xs)` を 1000000 回(名前の無い関数、器を作り直す) | 110000000 |
| t_hof_cap | `sc k l ? fold $[a x ? a + x * k] 0 l` を 3000000 回(囲む関数の仮引数を捕まえる) | 495000000 |
| t_hof_par | `(ap $fib 37) + (ap $fib 37)` の `_s`・`_p2`・`_p4`(特殊化の後で並列に分かれる) | 48315634 |

見るもの: `_hof` が `_dir` とほぼ同じ時間か(疑似カーネルでは 4 題材とも命令数が完全に同じ)。`t_hof_par_p4` が直列の 2 倍近いか。答えが違えば特殊化の誤りなので報告してほしい。

## クロックと制限の記録(続き 2)

並列の各周(`_rounds`)と対照(`対照_並行N本`)の間、cpu0 の周波数(100 ms ごと)・温度・`vcgencmd get_throttled`(500 ms ごと)を拾い、備考に書く。
`実行中の cpu0 周波数 A〜B MHz・制限ビット 0x…` の読み方: bit0 電圧低下・bit1 周波数上限・bit2 制限中・bit3 温度上限(いまの値だけ。起動後に一度でも立った印の 0x5000x は除く)。
遅い周が出たときは `遅い周ほど周波数が低いか` に、周ごとの秒と周波数を並べる。Pi 3 A+ の前回のレポートでは `get_throttled` が `0x50005`(電圧低下と制限中)で、直列の loop を 4 本同時に走らせると 1 本より遅くなっていた(`--par` に依らない)。
実行中の周波数は `vcgencmd measure_clock arm`(実際の ARM クロック)を優先して読む(無ければ `scaling_cur_freq`)。Pi 3 A+ の記録では `scaling_cur_freq` が制限中も 1400 MHz のままだった。
