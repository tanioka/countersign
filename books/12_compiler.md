# 第12巻『Sign のコンパイラ』

Sign のプログラムを AArch64 の機械語にする `sign_asm.py` の使い方と中身。

## 第1章 はじめに

Sign のコンパイラは、プログラムを AArch64(Raspberry Pi などの 64 ビット ARM)の命令にして、インタープリタと同じ答えを出す道具です。この巻では、使い方、出てくるコードの読み方、できないことの順に説明します。

### 印の読み方

この巻では、結果の由来を2つに分けて書きます。

- **【仕様】** 設計者の仕様に書かれている動き。たとえば Int の溢れは罠(止まる)になる、という決まり。
- **【実装】** このコンパイラが決めた動き。仕様に書かれていないところで、将来変わるかもしれません。たとえば `linux` 向けの起動部、10 進の表示、`--elf` で実行ファイルを作る手順。

最初に見た形が頭に残るので、仕様どおりのものと実装だけのものを混ぜないように書いています。

### 前提

- 例は既定の読みで書いています。`--strict` は第7章だけで扱います。
- コンパイラが出せるのは AArch64 だけです。この巻の例は、この環境が x86 の Linux で実機がないため、付属のエミュレータ(`test_asm.py` の中の `Cpu`)で動かして答えを確かめています。実機(Raspberry Pi)での実行は、第11巻の手順で行います。
- コンパイラが出せない形があります。出せないときは、理由を言って止まります(第8章)。

## 第2章 最初の一歩

驚乗を 20 で計算するプログラム `fact.sn` を、アセンブリにして答えを確かめます。

```
fact : n ?
	n <= 1 : 1
	n * (fact (n - 1))
fact 20
```

まずインタープリタの答えです。

```
$ python3 sign.py fact.sn
2432902008176640000
```

### アセンブリを出す

```
$ python3 sign.py --asm fact.sn --target=linux -o fact.s
書きました: fact.s
```

`fact.s` は 83 行です。先頭は、関数 `fact` の本体です。

```
fact:
	stp x29, x30, [sp, #-48]!  // フレーム 48 バイト
	mov x29, sp
	cmp x0, #1
	b.gt .L3
	mov x0, #1
	b .L2
.L3:
	str x0, [x29, #24]  // 途中の値はフレームへ
	subs x0, x0, #1
	ccmp xzr, x0, #1, vc
	b.vs .Ltrap
	bl fact
	ldr x9, [x29, #24]
	mul x11, x9, x0
	smulh x12, x9, x0  // 積の上の語
	cmp x12, x11, asr #63  // 上の語が下の語の符号の伸びでなければ溢れた
	ccmp xzr, x11, #1, eq
	b.vs .Ltrap
	mov x0, x11
.L2:
	ldp x29, x30, [sp], #48  // フレームを戻す
	ret
```

読むときの目印です。

- 引数 `n` は `x0` で渡り、答えも `x0` で返ります(AAPCS64 の決まり)。
- `n <= 1 : 1` の行は、`cmp` と `b.gt` になります。
- `n - 1` は `subs` で、溢れたときは `.Ltrap` へ飛びます。
- `n * (fact ...)` は `mul` と `smulh` で、積が 64 ビットに収まらないときも `.Ltrap` へ飛びます。

### 実行ファイルを作る

```
$ python3 sign.py --asm fact.sn --target=linux --elf=fact
書きました: fact(AArch64 の静的な ELF)
```

`fact` は 1176 バイトの AArch64 用の実行ファイルです(clang と ld.lld が要ります)。x86 のマシンでは動きません。Raspberry Pi など AArch64 の Linux で実行すると、`2432902008176640000` と表示して終わるはずです。この環境では、同じアセンブリを付属のエミュレータで動かして確かめました(表示 `2432902008176640000`、終了コード 0)。実機では未確認です。

中身は `llvm-objdump -d` で見られます。

```
$ llvm-objdump -d --no-show-raw-insn fact
0000000000210120 <fact>:
  210120:  stp  x29, x30, [sp, #-0x30]!
  210124:  mov  x29, sp
  210128:  cmp  x0, #0x1
  21012c:  b.gt 0x210138 <fact+0x18>
  ...
```

`sign.py` が `fact.sn: 警告(lint L2): _sign_print_int …` という知らせを出すことがあります。これは、`linux` 向けの起動部の表示ルーチン(`_sign_print_int`)についての、簡単な検査(lint)の知らせです。この例では答えは変わりませんでした。止めるには `--no-lint` を付けます。

### 溢れるとき

`fact 21` は 64 ビットの Int に収まりません。インタープリタ(`--check-int`)も、エミュレータで動かしたアセンブリも、答えを出さず罠(止まる)になります。アセンブリの側では、`.Ltrap` の先で `wfi` を繰り返して止まります。

- 【仕様】溢れは罠になる(integer_overflow.md §1)。
- 【実装】罠のときの振る舞いは `wfi` で止めること。`x16` に原因の印を置くこと。

## 第3章 ターゲットを選ぶ

`--target` は「出したコードをどこで動かすか」を選びます。2種類で、省略すると `bare` です。無効な名前を与えると、`--target は bare か linux です(nope)` と言って終わります。

| ターゲット | 出るもの | 答えの行き先 | 使いどころ |
|---|---|---|---|
| `bare`(既定) | 関数と `_.main` まで | `_.main` が `x0` で返す | 設計者の aarch64_rpi などベアメタル。起動部は別に用意する |
| `linux` | 上に加えて `_start`、10 進の表示、`exit` | 標準出力に 1 行、終了コード 0 | Raspberry Pi などの Linux で単体の実行ファイルにする |

- 【仕様】設計者のターゲット(aarch64_rpi、qemu、firmware)はベアメタルです。`bare` はその側の形です。ただし設計者の資料には起動部(qemu/start.s)が無く、`bare` は起動部の無い形です。
- 【実装】`linux` の足場(`_start`、`_sign_print_int`、`exit` の svc)は実装だけのものです。今後変わる可能性があります。

### 同じプログラムで見比べる

`1 + 2` を `bare` で出すと、`_.main` は `x0` に 3 を置いて `ret` するだけです。

```
_.main:
	stp x29, x30, [sp, #-16]!  // フレーム 16 バイト
	mov x29, sp
	mov x0, #1
	adds x0, x0, #2
	ccmp xzr, x0, #1, vc  // 溢れずに INT64_MIN に着いた結果も罠
	b.vs .Ltrap
	ldp x29, x30, [sp], #16  // フレームを戻す
	ret
```

`--target=linux` を付けると、この後ろに `_start` と `_sign_print_int` が続き、`_start` が `_.main` を呼んでから 10 進で表示して `exit(0)` します。同じ関数の部分(上の `fact` の本体)は、どちらのターゲットでも同じです。`fact.sn` で2つの出力を `diff` で比べると、違うのは末尾に足される 40 行(`_start` と表示ルーチン)だけです(`bare` は 43 行、`linux` は 83 行)。

### 「値が無い」答えの行き先

答えが `__`(欠け)のとき、`_.main` は `x0` に特別な値 `0x8000000000000000`(INT64_MIN)を置きます。`3 < 2` を出すと、次のようになります。

```
	mov x9, #3
	cmp x9, #2
	b.ge .L1
	mov x0, #3
	b .L2
.L1:
	movz x0, #0x8000, lsl #48  // __
.L2:
```

`linux` の起動部を付けてエミュレータで動かすと、標準出力に `__` と表示して終わりました。この「欠け」の表し方(`0x8000000000000000`)は、設計者の資料(target_info.js の `UNIT_NICHE_ASM`)のものです(【仕様】)。Int の値域は -(2^63 - 1) 〜 2^63 - 1 で、INT64_MIN は値になりません。和・差・積がちょうど INT64_MIN に着いても罠にします(【仕様】)。上の `ccmp xzr, x0, #1, vc` の行がそれを確かめるのは、このコンパイラのやり方です(【実装】)。

### 選び方

- 手元の Raspberry Pi の Linux で試す → `linux` と `--elf`。
- ベアメタルの起動部と組み合わせる → `bare` を出して、自分の起動部から `_.main` を呼ぶ。
- 装置(GPIO など)を実機の Linux で動かす → `linux` に `--real-dev` を付ける(第6章)。

## 第4章 値と器の大きさ

整数はレジスタ 1 つで済みますが、リストは「何個入るか」が実行するまで分からないことがあります。そこでこのコンパイラは、返す器の大きさを「上限」で見積もり、その場所を呼ぶ側が用意します。

### 上限の式

返す器の大きさの上限は、次の形で表します。

```latex
\text{konst} + \sum_i \text{coef}_i \times \lVert p_i \rVert
```

- `konst` は字面で決まる定数の分、`p_i` は器の仮引数、`coef_i` はその器が何回展開されるか、`‖p_i‖` はその器の長さです。
- 枝が分かれるときは、枝ごとの最大を取ります。
- 【仕様】この式と、呼ぶ側が置き場を取るという決まりは、設計者の資料(stack_abi.md §4.7、pass4.js の `returnSizeBound`)のものです。
- 【実装】このコンパイラはその一部だけを実装しています。食う再帰(添字で回る再帰)の見積もりや、器の要素が器のときの一部は未実装です(第8章)。

### 例: リストを 2 回並べて 7 を添える

```
dup : xs ?
	(xs xs 7)
dup (1 2 3)
```

答えは `[[1, 2, 3], [1, 2, 3], 7]` で、インタープリタとエミレータで動かしたアセンブリが一致しました。呼ぶ側 `_.main` は次のように置き場を用意します。

```
	mov x1, #3  // 長さ
	sub sp, sp, #80  // 返値スロット(上界 9 語)。呼ぶ側が取る
	mov x8, sp
	mov x15, #3  // 記述子の数 K
	...
	bl dup
	mov sp, x29  // sub sp で取った置き場を捨てる
```

読み方です。

- `x8` は置き場の先頭、`x15` は入る記述子の数 K です。`(xs xs 7)` は要素が 3 つなので K = 3 です。
- 置き場の語数は 2K + 2 + M で、ここでは 6 + 2 + 1 = 9 語(72 バイト)です。M は要素を展開して置く内容の語数です。`sub sp, sp, #80` は 16 バイトの境に切り上げた値です。
- 呼ばれた `dup` は、書く前に `cmp x10, #3` で個数を確かめ、入らなければ器を作らず `__`(長さ 0)を返します。リストの長さを式に入れる関数では、呼ぶ側が実行時に実引数の長さから式を計算して `sub sp` します。

### この上限を信じてよいか

上限を証明できない形もあります。そのときの既定の動きは、上限を見積もりで通して、実行時に入るかを確かめ、見積もりにしたことを information で名指することです(仕様どおりと、`--help` にあります)。`--no-estimate` を付けると、見積もりでは通さなくなります。

- 【実装】Linux 向けで、累積が作業領域に収まらないとわかったときは、`__` を返す前に標準エラーへ `sign: work area overflow (result is __)` を 1 行出します。

## 第5章 関数・末尾呼び出し・最適化

Sign の関数は、AArch64 の関数呼び出しの約束(AAPCS64)どおりに出します。引数は `x0`、`x1`…、答えは `x0` です。この章では、末尾呼び出しがループになることと、最適化を段ごとに切れることを見ます。

### 末尾呼び出しはループになる

1 から n までの和を、末尾再帰で計算します。

```
sum : n acc ?
	n < 1 : acc
	sum (n - 1) (acc + n)
sum 100000 0
```

答えは `5000050000` です(エミュレータで確かめました)。`sum` の本体は次のようになります。自分を呼ぶ行が `bl` でなく `b .L1` になっています。

```
sum:
	stp x29, x30, [sp, #-80]!
	mov x29, sp
	...
	mov x19, x0  // 仮引数 n
	mov x20, x1  // 仮引数 acc
.L1:
	cmp x19, #1
	b.ge .L3
	mov x0, x20  // acc
	b .L2
.L3:
	subs x9, x19, #1
	ccmp xzr, x9, #1, vc
	b.vs .Ltrap
	mov x21, x9  // 実引数
	adds x9, x20, x19
	ccmp xzr, x9, #1, vc  // 溢れずに INT64_MIN に着いた結果も罠
	b.vs .Ltrap
	mov x19, x21  // 仮引数 n を更新
	mov x20, x9  // 仮引数 acc を更新
	b .L1  // 自分への末尾呼び出し
.L2:
	...
	ret
```

追いかける目印です。

- 仮引数 `n`、`acc` はレジスタ `x19`、`x20` に置かれ、ループの間メモリに触れません。
- 次の回の引数は、まず一時的に `x21` と `x9` に計算してから同時に更新します。これで、`acc` の計算が更新済みの `n` を読むことがないようにしています。
- 再帰の深さがどんなに増えても、スタックは使いません。
- 【仕様】「末尾の呼び出し」とは何かは、設計者の仕様にあります。
- 【実装】自分への末尾呼び出しをレジスタの更新とジャンプにするのはこのコンパイラのやり方で、仕様が求めるものではありません。

### 最適化の段を切る

先のアセンブリは最適化ありの出力です。`--no-opt` を付けると、式を木のまま素直に作った形になります。

```
.L1:
	ldr x9, [x29, #16]  // n
	mov x10, #1
	cmp x9, x10
	b.ge .L3
	ldr x0, [x29, #24]  // acc
	b .L2
.L3:
	ldr x0, [x29, #16]  // n
	mov x9, x0
	mov x10, #1
	subs x9, x9, x10
	...
	str x0, [x29, #32]  // 実引数
```

仮引数がフレームのメモリに置かれ、計算のたびに読み書きします。`sum` を含むプログラム全体のアセンブリ(`bare`)は、最適化ありで 50 行、`--no-opt` で 59 行です。

段は次のフラグで個別に切れます。すべて、答えは変わりません。

| フラグ | 切るもの |
|---|---|
| `--no-opt` | 関数ごとの制御フロー解析にもとづく最適化(`sign_opt.py`) |
| `--no-peephole` | 窓の置き換え(`sign_peep.py`) |
| `--no-fuse` | `[op] (map $g xs)` を添字で回る補助関数へ書き換える段 |
| `--no-share` | 同じ算術式を使い回す段 |
| `--no-hoist` | 自己再帰で変わらない仮引数だけでできた算術式を扱う段(`sign_fuse.lazy_invariants`) |
| `--no-scalar` | レコードをスカラーにばらす段 |
| `--no-neon` | Vector の計算に NEON の命令を使う段(調べた事実と段取りは DESIGN_NEON.md) |
| `--no-lint` | 出したコードの簡単な検査の知らせ |

上の `sum`(引数 1000)を全部のフラグで出してエミュレータで動かしたところ、どれも `500500` でした。最適化が答えを変えていないかを確かめるときは、このようにフラグを切って見比べます。このフラグと段はすべて【実装】です。

### 注意

引数 100000 の `sum` を、最適化を切ったアセンブリでエミュレータにかけると、エミュレータが「命令数の上限」で止まりました。これはエミュレータの制限で、コードの誤りではありません。同じ理由で、この巻の長いループの例は実機で確かめることを勧めます。

## 第6章 装置と入出力

Sign のプログラムは、「決まった番地」への `#`(書く)と `@`(読む)で装置を動かします。コンパイラはこれを、既定では「その番地への 64 ビットの書き読み」として出し、`--real-dev` を付けると、実機の Linux の装置を動かす呼び出しに置き換えます。

### 例: 1 文字ずつ写す echo

`echo.sn` は、標準入力を 1 文字ずつ読んでそのまま出力するプログラムです。UART の番地を `0x9000000` として、「読む → 書く」を繰り返します(入力が終わると読みが `__`)。

```
uart : 0x9000000

seq2 : a b ? b

go : c ?
	c = __ : 0
	seq2 (uart # c) (go (@uart))

go (@uart)
```

入力 `hello` を与えて、インタープリタと、アセンブリ+装置付きエミュレータ(`emu_dev.py`)を見比べたところ、どちらも `hello` の後に最後の答え `__` を表示して終わりました。

### 既定の出力: 番地へ直接

`uart # c` は、次のようになります(番地をフレームに置いてから書きます)。

```
	movz x0, #0x900, lsl #16  // uart
	str x0, [x29, #24]  // 番地
	mov x0, x9  // c
	ldr x9, [x29, #24]
	str x0, [x9]  // 64 ビットで書く
```

`@uart` は `ldr x0, [x0]` で、`__`(`0x8000000000000000`)と比べて「読めなかった」を判断します。このコードは、その番地に装置が実際にあることを前提にします。ベアメタルならそのとおりですが、普通の Linux のプロセスではこの番地は使えません。

- 【実装】「書かれていない」を `__` とするのはインタープリタの装置の設計で、実機にはその区別がありません(生成コードのコメントもそう言っています)。
- 【実装】装置の番地表(UART、I2C、SPI、描画、入力、`sys` など)と、`sys`(`0x9400000`)の使い方は、この実装で決めたものです(proposal_io_devices.md)。

### `--real-dev`: 実機の Linux に繋ぐ

```
$ python3 sign.py --asm echo.sn --target=linux --real-dev -o echo_real.s
```

同じ `echo.sn` で、アセンブリは 128 行から 4268 行になります。番地へ直接書く行が次のように置き換わり、装置ごとの中継ルーチン(`_sign_dev_st`、`_sign_dev_ld`、`_sign_dev_i2c`、`_sign_dev_spi` など)が後ろに続きます。

```
	bl _sign_dev_st  // 装置への書き込み(実機の中継。sign_realdev.py)
	...
	bl _sign_dev_ld  // 装置からの読み(実機の中継。sign_realdev.py)
```

- 標準入出力、時計、`/dev/i2c-N`、`/dev/gpiochip0` を使う中継が入ります。
- `sys`(`0x9400000`)は、ファイルの読み書きや時刻を Linux のシステムコール(`read`、`write`、`openat2`、`close`、`clock_gettime`、`lseek`)に対応させます。開けるファイルは作業フォルダの中だけで、fd は 3〜18。
- 【実装】これらはすべて実装だけのものです。実機では未実行です(この環境は x86 で、エミュレータで試しています)。
- SQLite の装置(`0x9A00000`)を実機で動かすには `--real-db` を付けます(`libsqlite3` と `gcc` が要り、`--elf` とは併せられません)。

### ディスプレイの大きさとこま数

`--display=幅x高` は描画装置の大きさ(既定 64x32)、`--fps=N` は `tick` を持つファイルを実機で回すときの 1 秒あたりのこま数(既定 60)です。こちらも【実装】の設定です。

## 第7章 `--strict --asm`

`--strict` は、仕様の読みをインタープリタで試すスイッチです。ここで「既定の読み」と「仕様の読み」が食い違う形があり、コンパイラは元々、既定の読みに合わせています。`--asm` に `--strict` を付けると、仕様の読みと同じ答えになるコードを出します。

- 【仕様】`--strict` の読みは、設計者の仕様(coproduct_spec)の読みです。
- 【実装】`--strict --asm` の作り方はこのコンパイラのものです。**別の道**で、既定の道は変えていません。

### 何をするか

構文木を書き換えてから、いつもの道でコードを出します。書き換える形は次の 4 つです。

| # | 既定の読み | 仕様(`--strict`)の読み |
|---|---|---|
| 1 | `x ' 名前`、`名前 @ x`(鍵が名前) | 鍵の名前は `!_`(`__`)。R64 |
| 2 | 逆適用 `c f` | `c` のまま。`f` は落とす |
| 3 | 最後でない行 `c : v`。`v` が `!_` になりうる | 条件と値を `&` でつなぐ形。値が `!_` なら次の行へ進むc & v) |
| 4 | 本体の行 `y : …`(`y` が仮引数かファイルの値) | 条件の行。名前を定義する行ではありません |

上の 4 つのどれかに当たる形だけを書き換え、それ以外はそのままです。書き換えで直せない形があると、`--strict の読みにできない形があります…` と言って止まります。

### 例 1: 鍵が名前

```
f : i ? ([9 9 3] ' i)

f 1
```

| 読み | 答え |
|---|---|
| 既定(インタープリタ、`--asm` とも) | `9` |
| `--strict --asm`(エミュレータで実行) | `__` |

この `--strict` の答え `__` は、判定に使っているインタープリタの `--strict` の読み(`test_asm_strict.py`)と一致しました。

### 例 4: 本体の行の左が名前だけ

```
f : x y ?
	5 : ((x % y) > (y % x))
	y : 2
	7

f 100 1
```

| 読み | 答え |
|---|---|
| 既定(インタープリタ、`--asm` とも) | `__` |
| `--strict --asm`(エミュレータで実行) | `2` |

### 限界

- 【実装】この書き換えは上の 4 形だけです。インタープリタの `--strict` の全ての違いを写すものではありません。この 4 形と、形を変えない例が、`test_asm_strict.py` でインタープリタの `--strict` と合うことを確かめています(6 例)。
- 【実装】乱数で作ったプログラムでも `--strict` との食い違いは見つかりませんでした(strict_diff/ のツール)。
- 【実装】既定の読みのときと同じで、コンパイラが出せない形はここでも出せません(第8章)。

## 第8章 限界と今後

この章は、コンパイラがやらないことをまとめます。出せない形は、黙って間違ったコードを出さず、理由を言って止まります。

### 出せないときの止まり方

| 形 | コンパイラの言い方 |
|---|---|
| 引数が足りない呼び出し(`g : a b ? a + b` の `g 1`) | `g は引数 2 個の関数ですが、1 個で呼ばれています(部分適用・余った引数はまだ出せません)` |
| 文法の誤り(`( ( )`) | `読めません(SyntaxError): 閉じ括弧がありません` |
| ファイルが無い | `エラー: nofile.sn を読めません(…)` |
| 知らない `--target` | `エラー: --target は bare か linux です(nope)` |
| 知らないオプション | エラーと使い方を出して終わり |

これらはどれも追跡(Traceback)を出さず、終了コード 1 で終わります(`test_asm.py` が確かめています)。【実装】のふるまいです。

### まだ出せないもの

- **AArch64 以外**。x86-64(Windows を含む)は出せません。`--target` には `bare` と `linux` しかありません。
- **部分適用と余った引数**。上の表のとおりです。
- **小数(Float)を含むプログラムの多く**。`1.5 + 2.5` は出せませんと止まります。Vector を NEON で計算する計画は DESIGN_NEON.md にあります。
- **返す器の上限の一部の形**。実装メモによると、添字で回る再帰の見積もりなどの一部を設計者の `returnSizeBound` どおりにはまだ実装していません。`--no-estimate` を付けると、この種の形は断られます。
- **実機での確認**。この巻の答えは、すべてエミュレータで確かめたものです。Raspberry Pi での実行結果と、実機の装置(`--real-dev`)は未確認です。

### 大きさの決まらないデータ

答えの器の大きさを、呼ぶ前に上限で見積もれるのがこのコンパイラの使い方です(第4章)。見積もれない大きさのデータ(実行中にどこまでも伸びるリストや文字列)をどう扱うかは、設計者と相談する点です。実行時に伸ばす仕組み(ヒープのような領域)は、実装メモでは「仕様の核に反する」と読んでいます。このため、今のコンパイラはこれを入れていません(【実装】の読み。設計者の返事は未定)。

### このコンパイラを Sign で書くとすると

コンパイラを Sign 自身で書いて、自分をコンパイルすること(セルフホスト)は、この巻の時点ではできません。理由の一つは上の「大きさの決まらないデータ」です。ソースや構文木は大きさが入力で決まり、計算を始める前に上限を決めることが難しいからです。このことは設計者への問いとして残しています。
