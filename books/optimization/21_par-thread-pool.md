# 第21章 --par=N スレッドプール

## 何を並列にするか

`sign_asmpar.py` は、純粋な整数関数の**兄弟の呼び出し**をスレッドの池に渡す。ファイル先頭の説明文は、この機能を「仕様に無い追加で、値は変えない」と明記する。例として挙げているのは `fib (n - 1) + fib (n - 2)` である。

並列にできる条件は次のとおり。

| 条件 | 内容 |
| --- | --- |
| 演算 | `+ - * / % && \|\| ;; << >>` の両辺が純粋な整数関数の呼び出し |
| 純粋な整数関数 | 仮引数が全部 Int、戻り値が Int、本体が整数の字面・仮引数・定数・算術・比べ・条件の行・同じ性質の関数の呼び出しだけ(メモリ・装置・器・文字列に触れない) |
| 実引数 | 整数の字面・仮引数・定数・`+ - *` だけ(副作用が無く、`__` にならない) |

3 項以上の左結合の連なり `a + b + c + d`(葉が全部そうした呼び出し)は、最後の 1 つ以外を全部仕事に出し、畳み込みは元の演算で左から行う。外れる式は今までどおり直列のコードを出す。同じ式に直列版も残して、実行時に選ぶ。

並列にしてよい理由は、第20章のとおり、副作用が無い式どうしは順序を入れ替えてよいからである。溢れの罠は労働者の中で起きても、直列と同じに止まる(ファイル先頭の説明文)。このときの罠の起きる時と場所は、第22章の投機実行と巡り戻しで扱う。

## 仕組み: 入れ物・待ち行列・労働者・合流

ここからは `sign_asmpar.py` の説明文を読んで要点をまとめる。実際のコードの細部は追っていない。

| 部品 | 役割 |
| --- | --- |
| 仕事の入れ物 | 呼び側のフレームに置く 5+k 語。状態(0 出さない・1 待ち・2 走行中・3 終わり・4 呼び側が奪った)、包みの番地、答え、入れ子の段、かかった時計の数、実引数 |
| 待ち行列 | 64 個の輪。先入れ先出し |
| 労働者(N-1 本) | 最初の submit で `clone(CLONE_THREAD)` して作る。積みは 64 MiB の mmap。作れなければ全部直列 |
| `_sign_par_submit` | 入れ物を待ち行列に入れ、futex で眠っている労働者を 1 つ起こす |
| `_sign_par_join` | まだ待ち行列にある仕事を**奪って自分で走らせる**。走行中なら futex で待つ(待つ間も他の仕事を走らせる) |

待ち行列と状態の遷移はスピンロック 1 つで守る(区間は数命令)。「合流で奴う」という設計によって、スレッドが足りないときや労働者が作れないときでも、呼び側が自分で計算して答えが出る。

粒度を決めるのは二つの仕掛けである。

1. **空き。** 数の箱(`_sign_par_load` = 待ち行列の仕事 + 労働者が走らせている仕事)が N-1 以上なら空きの労働者が無いので、その所は直列。
2. **軽さ。** 左の仕事が時計の刀み(`cntvct_el0`)で 100 未満の「軽い」仕事を直列にする。軽さを何で覚えるかが第23章の主題である(既定は積みの深さで覚える `--par-relight`)。

## 実測: Raspberry Pi 4 での 7 本

測定は 2026-11-23 の再測定(`pi_results/pi_check_pi4_relight/report.json`、Pi 4 Model B Rev 1.1、4 コア)の結果である。ここでは記録をこのコンテナで読み直し、各 5 周の平均を計算した(記録の「最短」ではない)。単位は秒。`_s` は直列、`_p2` はスレッド 2 本、`_p4` は新しい既定(積みの深さで軽さを覚える)、`_p4site` は古い既定(呼び出し位置ごとの数え)。

| プログラム | 直列 | `_p2` | `_p4`(新) | `_p4site`(旧) | 直列に対する倍率 新 / 旧 |
| --- | --- | --- | --- | --- | --- |
| fib | 0.82 | 0.54 | 0.39 | 0.49 | 2.1 / 1.7 |
| fib1 | 1.08 | 0.87 | 0.50 | 0.71 | 2.1 / 1.5 |
| fib4 | 1.64 | 1.07 | 0.59 | 0.55 | 2.8 / 3.0 |
| args | 1.07 | 0.74 | 0.45 | 0.59 | 2.4 / 1.8 |
| local | 0.76 | 0.54 | 0.35 | 0.53 | 2.2 / 1.4 |
| list | 0.83 | 0.50 | 0.33 | 0.55 | 2.5 / 1.5 |
| loop | 2.67 | 1.34 | 0.69 | 0.70 | 3.9 / 3.8 |

読み取れることは三つ。

- 4 スレッドの新しい既定は、どのプログラムでも直列の 2.1〜3.9 倍速かった。答えはどれも直列と同じである。
- 新旧の差は第23章で扱う。ここでは、fib4 と loop では新旧がほぼ同じで、他の 5 本で新しい既定のほうが速いとだけ述べる。
- 2 スレッドは直列の 1.2〜2.0 倍で、スレッドを増やすほど速くなる傾向はあるが、スレッド数に比例してはいない。

記録の備考では、直列の `fib` は実行中の ARM クロックが 700〜1500 MHz に変わっていた(`_p4` は 1500 MHz で固定)。周回ごとの直列の時間は 0.82 秒でほぼ一定で、このクロック変動が倍率を歪めている可能性は小さいが、確かめてはいない。

## 限界と、文書の遅れ、仕様と実装の分け

**確かめたこと。** この再測定では、145 件すべてで実機と期待の食い違いが 0 であった(実装ノートの記録)。並列の `_p*` はどれも直列 `_s` と同じ答えを出した。

**限界。**

- Linux 用(`--target=linux`)だけで、時計の長さは `cntvct_el0` の周波数しだい(Pi 4 は 54 MHz で 1000 時計が約 18 マイクロ秒)。
- fib4 のように、新旧の差が出ないプログラムがある。記録では旧い既定でもこの回は fib4 に遅い周が出なかったので、「遅い周が消えた」と言えるのは他のプログラムに限る(第23章)。
- 測定は 4 コアの Pi 4 で、この 7 本だけを走らせた結果である。他のプロセスがコアを占めている状況での測定はしていない。また、記録は別の機種(Pi 3 A+)ではこの結果と違う傾向を示す(第23章)。

**文書の遅れ。** `sign_asmpar.py` の先頭の説明文には、今のコードと合わない箇所がある。記録を読んでの気づきである。

| 説明文の記述 | 今の状態 |
| --- | --- |
| 「軽さ: 1000 時計より短かった回が 3 回続いたら以後ずっと直列」 | 既定は `RELIGHT = True`、境は 100。説明文は古い方式の説明 |
| 「実機では未実行」 | Pi 4 で実行済み(この章の表) |
| 仮引数は全部 Int | `eligible` のコメントは「Int か、Int のリスト・文字列(読むだけ)」とする |

読者が説明文をそのまま信じると、今の振る舞いと食い違う。ここでは実際のコード(`RELIGHT`)と記録を優先して記した。

**仕様と実装の分け。** 並列化は仕様に無い追加で、純粋な整数関数の式に限り、観測(終わり方・値・メモリ・警告)を変えないという約束だけが仕様と繋がる。スレッドの数・待ち行列の大きさ(64)・軽さの境(100)は実装の選択である。
