# 第28章 仕様が決めていないところでは最適化しない

## 何が未決か

実装が「ここは決められない」として設計者への問いに回しているのは、文書どうしが食い違うか、仕様が何も書いていない箇所である。`designer_questions_one_page_2026-11-23.md`(仕様 `johnny-shaman/Sign` 0114ac8a を読み直して残った 6 件)から、この章で使う 4 件を挙げる。

| 問い | 例 | 一方の文書 | 他方の文書 |
| --- | --- | --- | --- |
| A3 | `9223372036854775807 + 2`(Int の溢れ) | 罠で止まる(`integer_overflow.md` など。利用者の裁定 2026-10-11) | `!_`(value\_spec V5。設計者の答え 2026-10-27/28) |
| D1 | 実行時に大きさが決まるデータを `--asm` で扱いたい | 確保(`#`・`##`・`###`)がある(`memory_management.md` など) | 実行モデルはヒープを必要としない(`execution_model.md`)という読みもある。設計者への問いでは「確保を言語に残すか」を聞いている |
| D4 | `##x : 5`、`###x : 5` | export の印(型表の記述) | 確保の種類(`option_ms_schema.md`) |
| H1 | 書かれていない番地の読み出し | 仕様に決めが無い | — |

(D1 の「他方」の列は、質問書と実装ノートの記述を要約したもので、文面そのものではありません。)

この質問書で同じ名前を 2 回定義する「重複定義」は **A5** である(`compiler_pipeline.md` は先勝ち+information、もう一方は断る)。目次で「重複定義(D1・D4)」と書いていたのは番号の取り違えで、D1・D4 は確保の問いである。目次の該当箇所を直した。

ここで大事なのは、どれも「どちらが正しいか」を実装が決めることではないという点である。仕様は設計者のもので、実装の側で片方を直して見せることもしない。

## 速い方を選ぶと何が起きるか

未決の箇所は、答えが二つ以上ありうる。最適化が「こちらが正しい」と仮定して速くすると、設計者が逆を答えたときに観測が壊れる。理屈を A3 で整理する。以下は設計の考え方(筆者の整理)であり、テストの結果ではない。

- 設計者が「罠」(b)と答えるとすると、溢れ検査を消して「答えを出す」最適化は誤答になる。
- 設計者が「`!_`」(a)と答えるとすると、溢れ検査で罠にすること自体が誤りになる。
- どちらでも、「溢れの起きる時を変えない」(第16章)は守られている。罠の起きる場所を用意しておくことが、どちらの答えでも後で直せる基礎になる。

このように「断る・記録する」には、次の利点がある。

1. **後で直せる。** 設計者の答えが出たときに、直す場所が「未決」の行として見えている(第25章)。
2. **学習者が誤解しない。** 実装だけの振る舞いを「仕様」として見せない(最初に見たものが定着するから)。
3. **最適化の証拠にならない。** 未決の組を「一致」に数えないので、一致率が自動的に高く見えることがない。

## 実際の振る舞いを実行で示す

このコンテナで、同じプログラムを経路ごとに走らせた。

**A3: `9223372036854775807 + 2`**

| 経路 | 観測 |
| --- | --- |
| 既定モードの実行(`sign.py`) | `9223372036854775809`(溢れずに計算する) |
| `--strict` の評価器 | 空(`!_`)。知らせ `int-overflow`(答え 9223372036854775809 が範囲外という文面) |
| 機械語(エミュレータ) | 罠 |

**A5: `f : x ? 1` と `f : x ? 2` を同じファイルに続けて書き、`f 0`**

| 経路 | 観測 |
| --- | --- |
| 既定モード | `2` |
| `--strict` | 知らせ `name-duplicate`(先に書いた 1 番目が勝ち、2 番目は使われないという文面)。標準出力に値は出ない(`--strict` は最後の値を表示しない設計) |

**H1: `0x500000 # 5` のあと `@0x500008`(書いていない番地を読む)**

| 経路 | 観測 |
| --- | --- |
| 評価器 | 空(`__`) |
| 機械語 | 0 |

ここではどの経路も「最適化していない」結果であり、どれかを「正解」として直していない。表で見ると、既定モードと `--strict` と機械語で答えが三つに割れるのが A3 で、これを「最適化で統一」してはいけないという理由がこの表に現れている。

**限界。**

- 表の「既定モード」は旧い実装(alpha)との互換を保っている読みで、仕様ではありません。設計者の答えが出たとき、どれを合わせるかも設計者と相談です。
- この章の「未決」の一覧は 2026-11-23 時点の質問書による。答えが出れば古くなる。
- B1・C4 も未決だが、最適化の議論とは近くないのでここでは扱わない。
