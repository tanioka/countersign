# 第30章 この先へ

## ノートに「見送り」として残っているもの

この章は、この先にやることを思いつく。ただしこの章で述べる候補は、実装ノートに「見送り」「まだやっていない」として理由つきで残っているものに限る。目次にあった「プロファイルガイド付き最適化」や「レジスタ割り当ての改良」は、理由つきの記録をノートで見つけられなかったので、ここでは扱わない(「補助の呼びをまたぐ値の x19〜x25 への割り付け」は見送りの記録にあるが、これを「レジスタ割り当て」と同一視するのはこの章の解釈)。

| 候補 | ノートの記録 | 見送っている理由 |
| --- | --- | --- |
| 評価器の木を Python の関数の組に直す | 細かい削りでは動かなかった。効く見込みがあるのはこの方式だけ | `--strict` のゲートと位置情報(`POS`)との整合を取る大仕事。遅さで困る場面が出るまで見送り(第6章) |
| `--par` の実行環境(手書きの部分) | 実際にやっていない | 原子命令・syscall・TLS を含むので意図的に見送り |
| Cortex-A72 向けの並べ替えの調整 | まだやっていない | 実機では未実行とする記録と並べている |
| メモリ読みのループ外への移動 | まだやっていない | (理由の記述はこの章で確かめていない) |
| 輪を通るカウンタの整数範囲 | 見送り | 輪の辺は「通るたびに器の長さの総和が減る」を回る回数の根拠にしており、カウンタは長さを減らさない。直すには輪の検出・上界・検査に及ぶ設計変更が要る |
| 開始値が負の上向きカウンタ | 検討して見送り | 係数の鍵を拡張する必要があり、効果が小さい |
| `charset : utf32` | 見送り | 文字列の取り出し・コピー・連結・印字・`.rodata` が全部 1 バイト幅前提 |
| `addr # value` の MMIO | 見送り | 番地が処理系の仮想装置のもので実機の AArch64 上に無い。意味を決めるのは設計の領域 |

最後の 2 行は最適化ではなく機能の話だ。`addr # value` の見送りの理由は「設計の領域」という箇所で、仕様が決める話である。この章ではこれを今後の設計者への問いの候補として扱い、実装しない。

## どの候補も、同じ手順で進める

この本の各章を貫く手順は、次の 5 つに縮められる。

1. **先に観測を決める。** 変えてはいけないものは (終わり方, 値, メモリ, 警告) の組である(第3章)。
2. **先に測る。** どこが遅いか、何が変わったかを、同じ測り方で前後に測る(第4〜6章)。
3. **三つの道で突き合わせる。** 評価器・SIR・機械語に同じ観測を返させ、一致しないものは誤答・断り・罠・未決に分ける(第2章・第24〜25章)。
4. **実機で確かめる範囲を決める。** 確かめたものと確かめていないものを分けて書く(第26章・第29章)。
5. **仕様が決めていない所は足さない。** 食い違いは設計者への問いとして残す(第27〜28章)。

この先の候補を実装する前に、この 5 つのうち、どれが欠けているかを見るとよい。たとえば表の「輪を通るカウンタ」は、設計変更が輪の検出・上界・検査に及ぶので、まず 3 の突き合わせを増やしてから着手する、という順になる。

**やらないことも手順の一部。** 実装ノートには、同じ見送りでも「理由つき」と「測っていない」が混ざっている。前者は後から条件が変わったら見直す。後者は測ってから決める。この区別をそのまま残すと、次の人が同じ調査を繰り返さない。

## 限界

- 候補の表は実装ノートの記録を読んでまとめたもので、再実行や再確認はしていません。「見送りの理由」はノートの文言を縮めたものです。
- 目次に書いていた「プロファイルガイド付き最適化」「より強い範囲解析」「レジスタ割り当ての改良」は、理由つきの記録をノートで見つけられなかったので、この章の候補から外しました。範囲解析については、輪を通るカウンタなど個別の見送りだけを載せています。
- 5 つの手順は、この本の章をこの章で縮めたもので、ノート自身が定めた型ではありません。
- 候補の優先順位は付けていません。効果は測っていないからです。

**仕様由来と実装の選択。** 候補はどれも、仕様に書かれていない最適化か、実装の機能の話です。`addr # value` の意味や `charset : utf32` の扱いは、仕様が定めるべき点になりえます。その場合は実装ではなく設計者への問いになります(第27章)。
