# 第14章 デッドコードの除去

## 二種類のデッドコード

「死んでいるコード」には、粒度の違う二つがある。

| 種類 | 消す単位 | どこで消すか | 根拠 |
| --- | --- | --- | --- |
| 使われない関数 | 関数まるごと | `sign_asm.py` の `find_live`(コード生成の前) | 仕様 `compiler_pipeline.md` §4.1 |
| 読まれない命令 | 命令 1 本 | `sign_opt.py` の `dce`(命令列に対して) | 実装だけの最適化 |

どちらも「観測(終わり方・値・メモリ・警告)を変えない」ことを守る。前者は、呼ばれない関数は実行されないから観測に現れない。後者は、結果がどの道でも読まれない、かつ副作用が無い命令だけを消す。後者の「副作用が無い」の判定がこの章のややこしいところで、第16章の溢れ検査、第17章のピープホールと共通の安全の決まりになる。

## 使われない関数は出さない

`find_live` は、最上位の式から辿れる関数だけを集める(コードの説明文もこう書く)。そこに入らない関数は、型を決めることもコードを生成することもしない。このコンテナで試した。

```
used : n ?
	n + 1

unused : n ?
	n * 2

used 5
```

`python3 sign.py --asm` の出力(29 行)には `used` だけが現れ、`unused` のラベルも命令も無かった。終了コードは 0 で、診断も出なかった。仮引数を 2 つにした `unused : a b ?` でも同じだった。

仕様との対応は次のとおり。

- `compiler_pipeline.md` §4.1 は、「エントリポイントから静的に到達可能な型宇宙」だけを対象にするとし、「デッドコードは型付けされず、最終的にコード生成もされない」と書く。この節の例は未使用の struct/enum だが、実装の動き(使われない関数も出さない)は同じ考え方に沿う。関数へ適用してよいかは、私の読みである。
- `idiom_to_instructions.md` §1.6 は別のことを言う。「駆動されていない関数は診断になる」とし、仮引数の型が呼び出しから決まらない(直和・族)ときは「仮引数 X の渡し方が決まりません」を挙げる。今回試したのは仮引数が単純な関数だけで、この診断が出る形は試していない。この 2 つの文書の間をどう読むかは、設計者の読みを確かめる点として残す。

この節の結論は、「出さない」ことは観測を変えないが、「診断を出すかどうか」は仕様の読みしだいで、未確認ということである。

## 読まれない命令を消す

`sign_opt.py` の `dce` は、命令列を読み直して「結果がどの道でも読まれない、副作用の無い命令」を消す。仕組みは次の 2 段である。

1. 各命令の「読むレジスタ・書くレジスタ」を集め、制御フロー(分岐・戻り)をたどって、各点で「生きている」レジスタ・フラグ・フレームのスロットを不動点まで解く。
2. 消してよい命令(`rm`)で、書く先がその後のどの道でも生きていないものを死んだとして印をつける。消したあとに新しく死んでいる命令が出てくるので、変わらなくなるまで繰り返す。

「消してよい」の範囲はコードの `effect` が決める。読んで分かる限り、次のようになっている。

| 命令 | 消せるか | コード上の根拠 |
| --- | --- | --- |
| 計算命令(書き先が x0〜x28) | 消せる | `e.rm = int(d[1:]) < 29` |
| `cmp` `cmn` `tst` `ccmp` `ccmn` | 消せる(フラグが読まれないとき) | `e.rm = True` |
| フレーム(x29 相対)の読み・書き | 消せる(読まれないスロットへの保存) | `e.rm = True` |
| フレーム以外の番地の読み | **消さない** | 「フレームの読みは副作用なし(ほかの番地の読みは残す)」 |
| フレーム以外への書き・呼び出し(`bl`)・分岐・`ret` | **消さない** | `rm` を立てていない |
| 知らない命令 | **消さない** | `e.unk = True` として全部を読むとみなす |

罠の分岐 `b.vs` は、フラグを読む命令として扱う(`e.use = F_BIT`)。だから、第16章の `adds` → `ccmp` → `b.vs` の連なりでは、`ccmp` と `adds` がフラグを書いて、`b.vs` が読むので「生きている」と判定され、消されない。罠の行き先は「何も読まない」と決めている(ファイル先頭の説明文にある)。罠の起きる時を変えないという第16章の決まりは、分岐を消さないことと、フラグを書く命令を読まれているとみなすことで守られている。

説明文には「判らないものは何もしない(制御が読めない関数・x29 の番地を取る関数・知らない命令など)」ともある。読めない関数はスキップする。

## 実測と限界、仕様と実装の分け

このコンテナで、`fib 20` を `--asm` で出力し、命令とラベルを数えた(コメントとディレクティブを除く粗い数え方)。

| 設定 | 行数 |
| --- | --- |
| `SIGN_OPT=0 SIGN_PEEP=0`(どちらも切る) | 47 |
| `SIGN_OPT=0`(ピープホールだけ) | 34 |
| 既定(`SIGN_OPT=1` + ピープホール) | 31 |

ここで注意がある。`sign_opt.py` はデッドコード削除だけではなく、共通部分式・ループ不変式の移動・レジスタ割り付けをまとめて行う。上の 34→31 の 3 行がすべてデッドコード削除の効果とは言えない。デッドコード削除だけを切るスイッチが無いので、小さい 1 例の合計を示しただけである。実機の速さも測っていない。

仕様と実装の分けをまとめる。

| 分類 | 内容 |
| --- | --- |
| 仕様の記述と一致 | 到達できない定義を型付けしない・生成しない(§4.1 の記述を関数へ適用するのは私の読み) |
| 実装だけの選択 | 命令の死活解析と削除。判らない形は触れない。消す範囲(フレーム内の読み書きと計算だけ) |
| 確認していない | 未駆動の関数で診断を出すべきか(`idiom_to_instructions.md` §1.6)。仮引数が直和・族の形は試していない |

限界は三つ。

- 消すのはフレーム内の命令だけで、メモリへの書き込みや呼び出しは消さない。その分、消せる量は限られる。
- 呼びされるが結果を使わない関数呼び出し(純粋な関数の結果を捨てる場合など)を消すかは調べていない。`bl` は常に残す扱いである。
- 間違って消していないことの確認は、第24章の三者一致テストに頼る。この章でこの最適化だけを独立に検証したわけではない。
