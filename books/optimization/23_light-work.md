# 第23章 軽い仕事をどう扱うか

並列化では、極小の仕事を全部出すと手間で損をし、軽いと判定しすぎると分け直しが止まって偵る。この章は、その両方を実機の測定で見分けた経緯である。

## 問題: 周回ごとに速さが二つに割れる

実機(Pi 4、4 コア)で fib4 を 4 スレッドで走らせると、同じプログラム・同じバイナリなのに、ある周は約 0.54 秒で終わり、別の周は約 0.91 秒かかる。答えはどちらも直列と一致し、誤答はない。この「山」を「コアが空かなくなったせい」と見て最初は納得しかけた。

遅い周を「コア不足」で片づけると、ここで止まる。非決定的な遅れの原因を確かめずに直すと、直すたびに測定と合わなくなる。この章は、仮説を CPU 時間で判定して原因を突き止めた手順を示す。

## 診断: スレッドごとの CPU 時間

周回ごとの壁時計だけでは原因が分からないので、走行中に `/proc/<pid>/task/*/stat` を読んで、スレッドごとの CPU 時間を周ごとに記録した。仮説は二つ。「空きコアが減った(OS の都合)」なら全スレッドの CPU 時間が均等で、「仕事の分け方が偏った」なら特定の 1 本だけが長い。

| 版 | 壁時計(秒) | スレッドごとの CPU(ms) | 合計(ms) |
| --- | --- | --- | --- |
| fib4 `_p4`(遅い周) | 0.91–0.97 | 552 / 550 / **900–919** / 203 | 約 2210 |
| fib4 `_p4l0`(軽さ判定なし、遅い周) | 0.96–0.99 | 775 / 862 / 862 / 814 など、ほぼ均等 | 約 3300 |

結果は分け方の偏りであった。遅い周では 1 本が 900 ms(全体の 41%)、2 本が 550 ms、1 本は 203 ms で終わってあとは何もしていない。壁時計は最長の 1 本の時間に等しく、合計 CPU は速い周と同じ約 2.2 秒である。「空きコアが減った」という最初の見立ては、この測定で外れた。

軽さ判定を切った `_p4l0` は均等に分かれるが、合計 CPU が 2.2 → 3.3 秒に膨らむ。極小の仕事を出す・受ける手間の分で、壁時計は結局 0.96 秒と遅い。分け直しは起きても、細かすぎて損ということである。

## 一時的な案と、積みの深さで軽さを覚える方式

旧い既定(`--par-site-light`)は、呼び出し位置ごとに軽さを数え、軽いと 3 回続けて測れば以後ずっと直列にした(境は 1000)。再帰では深い所の仕事は軽いので、この永久の無効化が最初に起き、浅い所の重い仕事を出す機会も失われた。これが分け方の偏りの正体である。

最初の案は「軽いと測ったら次の K 回は出さず、K を倍々に伸ばす」だったが、見積もりで捨てた。再帰では試しがほぼ深い所(軽い)に当たるため、K を小さくすると(K=1024 で)極小の仕事の手間が仕事と同程度になり、大きくすると(K=65536 で)分け直しが数百 ms 遅れる。

決めたのは、積みの深さを手がかりにする方式(`--par-relight`)だ。

- 合流のあと左の仕事が軽ければ、その枠の `x29` をスレッドごとの覚え(TLS+0)に書く(今の覚えより浅い枠のときだけ)。重ければ何もしない。
- 仕事を出す前、覚えがあり今の枠がそれと同じか深ければ直列、浅ければ出す。
- 見送りは TLS+24 で数え、2^20 回ごとに覚えを消す(古い覚えで止まり続けない)。労働者が新しい仕事を取るたびにも消す。
- 位置の数え(`_sign_psN`)は使わない。永久の無効化がなくなる。軽さの境は 100 にした(理由は次の節)。

## 結果: Pi 4 と Pi 3 A+、既定にした理由と限界

Pi 4 では relight(`_p4r`)が旧い既定(`_p4`)より、loop を除く 6 題材すべてで平均で速く、遅い周も消えた。合計 CPU は増えない(`_p4l0` のような膨らみが無い)。

| 題材 | 旧い既定 平均(秒) | relight 平均(秒) |
| --- | --- | --- |
| fib | 0.43 | 0.34 |
| fib1 | 0.55 | 0.48 |
| fib4 | 0.84 | 0.62 |
| args | 0.56 | 0.46 |
| local | 0.49 | 0.34 |
| list | 0.48 | 0.31 |
| loop | 0.67 | 0.67 |

Pi 3 A+ でも relight は全題材で旧い既定以上だった。軽さの境は 100 が最良で、Pi 4(時計 54 MHz)でも 100 と 1000 に差がなかった。この 100 が両機で使える値なので、既定を `RELIGHT = True`、`LIGHT = 100` にした。

既定にしたあとの再測定(2026-11-23、Pi 4)では、新旧の既定を同じ実行で比べ、7 本中 5 本で平均が 2 割以上速かった。fib4 は同程度(0.59 秒対 0.55 秒)、loop は差がなかった。旧い既定でもこの回は fib4 に遅い周が出なかったので、山は毎回出るものではない。

限界が二つある。

- **fib4 の偏りが残る**: relight でも最長 640 ms 対均等 535 ms で、完全には均等にならない。fib も最初の分け方で決まる形が残る。
- **機種で答えが変わる**: Pi 3 A+ は 4 本同時に走らせると 1 本あたりが約 2.2 倍遅くなり、静的に分ける loop でも 4 本が 2 本に負ける。仕事の分け方では説明できなかった。「いつ並列化しないか」の答えは、機種を測って初めて出る。
