# 第16章 整数溢れ検査と最適化

## 溢れ検査の命令と、「罠」になる理由

Sign の整数の `+` `-` `*` は、結果が整数の範囲を超えると「罠(トラップ)」で止まる。机上の説明ではなく、`sign_asm.py` が実際に出す命令で示す。

| 演算 | 出す命令 | 意味 |
| --- | --- | --- |
| `+` | `adds` → `ccmp xzr, x9, #1, vc` → `b.vs .Ltrap` | 溢れたとき、または溢れずに `INT64_MIN` を超えた結果のとき罠 |
| `-` | `subs` → `ccmp xzr, x9, #1, vc` → `b.vs .Ltrap` | 同じ |
| `*` | `mul` + `smulh` → `cmp x12, x11, asr #63` → `ccmp xzr, x11, #1, eq` → `b.vs .Ltrap` | 積の上の語が下の語の符号の伸びでなければ溢れ |

`INT64_MIN` も罠にするのは、Sign の整数の値域が 0 を挨んで対称だからである(コードのコメントに「溢れずに INT64\_MIN に着いた結果も罠」とある)。この検査の形は、実装ノートの記録によれば `integer_overflow.md` §1.1 の表のとおりである。

罠になると、プログラムは `.Ltrap` へ飛んで止まる。実機の Raspberry Pi では終わり方が rc 124(20 秒の打ち切り)になる(第5章)。ここから最適化に関わる結論が出る。**これらの命令は、結果を計算するだけでなく、「ここで終わり方が変わりうる」場所でもある。**

## 動かせない・消せない、省けるのはどこか

罠になりうる命令は、次のどちらもしてはいけない。

- **消す。** 結果を使わない計算でも、溢れれば元のプログラムは止まる。消すと、止まらずに続けてしまう(終わり方が変わる)。
- **動かす。** 前に動かすと、本来はあとで起きる罠が先に起き、間にあったメモリへの書き込みや警告を飛ばす。後ろに動かすと、その間に起きる副作用が余分に見える。

どちらも第3章の観測(終わり方・値・メモリ・警告)を変える。だから最適化は「罠の起きる時を変えない」を守る。第17章のピープホールでも、罠の分岐は何も読まない物として扱い、命令の順を入れ替えない。

省けるのは、結果が溢れないと言い切れる場合だけである。コードには次の 2 箇所がある。

- 0 でない字面で割る `sdiv`。「商は被除数を超えず、値域は対称なので溢れない」とコメントして、検査を出さない。
- 符号反転 `neg`。「値域が 0 を挨んで対称」なので溢れないとして、検査を出さない。

どちらも「値域が対称」という性質だけが根拠で、速くするための赔けはしていない。

## 例: 不変式の持ち上げ(`lazy_invariants`)

ループの間で変わらない式を、毎回計算し直さないようにするのが不変式の持ち上げである。普通のコンパイラはこれをループの入口へ前倒しにする。しかし積や商を入口で計算すると、ループが一度もその式に到達しない場合にも溢れの罠が起きうる。罠の起きる時が変わるので、これはしてはいけない。

`sign_fuse.lazy_invariants` は、次の形の関数だけを対象にする。

- 自分を呈ぶ関数で、すべての自分呼びが同じ位置に同じ仮引数をそのまま渡す(不変)。
- 不変の仮引数だけでできた算術式(`+ - *` と字面で割る `/` `%`)。

この式に「遅延」の印をつけ、スロットを入口で「空」(`__`)にしておく。最初に式が必要になった所で、空なら評価して置き、あれば読む。**評価する場所は元のまま**なので、溢れの罠が起きる時も変わらない。違うのは 2 回目以降のループで再計算しないことだけである。

対象にしないものもある。足し引きだけの式は、スロットを読むのと命令数が同じで得がないので、対象にしない(コードの説明文にある理由)。この機能は既定で入っていて、`--no-hoist` で切れる。

## 仕様が決めること、未決(A3)、限界

この章の内容は、次の三つに分けて読む。

| 分類 | 内容 |
| --- | --- |
| 仕様の表に従う物 | 機械語での溢れ検査の形。実装ノートは `integer_overflow.md` §1.1 の表どおりと記録している |
| 処理系だけの選択 | 不変式の遅延。罠の起きる時を変えないという制約の範囲で、速くしている |
| 未決(A3) | 溢れたとき、評価器は `!_` を返して知らせ(information)を出し、機械語は罠で止まる |

A3 は、実装ノートの記録では仕様どうしの食い違い(documents と alpha1 、alpha1 の方が日付が新しい)とされている。設計者の答えが出ていないので、最適化の都合でどちらかに寄せない。評価器と機械語のどちらも今のままにして、テストでは「許容」ではなく「未決」と別に数える(第25章)。この章の最適化は、罠の起きる時を変えない作りにしている。設計者の答えがどちらになっても、この章の最適化をやり直す必要が出ないようにしたかったという意図であるが、それを確かめたわけではない。

限界は二つ。

- 省けるのは、溢れないと言い切れる場合(0 でない字面で割る・符号反転)だけで、一般の `+ - *` の検査はどこでも残る。
- 実機で「検査を残した分、どれだけ遅いか」はこの章では測っていない。
