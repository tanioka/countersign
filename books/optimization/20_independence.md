# 第20章 式の独立性を見つける

## 入れ替えてよいのは、副作用がぶつからない式

Sign の式は、引数を左から右へすべて先に評価する。引数どうしは互いの値を使わないので、メモリの書き込み・読み出し・デバイスの入出力がぶつからない限り、同時に評価しても値は同じになる。第20章は、この「ぶつからない」をどう判定するかを扱う。判定には `sign_plan.py` を使う。これは計画を出すだけの道具で、実際には並列に走らせない(仕様に無い追加の道具)。

判定の考え方は、各式を「読む番地の集合」と「書く番地の集合」の組(`Eff(r, w)`)に直すことだ。二つの式がぶつかるのは次のときだけである。

- どちらも同じ番地を書く
- 一方が書き、他方が同じ番地を読む

読むどうしはぶつからない。迷ったときは「ぶつかる」とみなす。番地が定数(名前つき定数や `+ - *` の計算を含む)で決まるものだけが「別の番地」と言え、計算で決まる番地はどの番地とも重なりうるとする。関数を引数として渡して呼ぶ形も、何を読み書きするか分からないので「何でもあり」とする。自分を呼ぶ再帰は、呼び先の組が変わらなくなるまで繰り返して組を求める。

例を 3 つ、`sign_plan.py` をここで走らせて確かめた。

| プログラム | 判定 | 理由(ツールの出力) |
| --- | --- | --- |
| `fib 20` + `fib 21`(重い純粋関数) | 同時にできる。理想の速さはコア 4 で高々 4.0 倍 | 副作用が無い。最上位の `+` の両辺、さらに fib の再帰が、分割統治の形 |
| `a n = 4096 # n` と `b n = 8192 # n` を `(a 1) + (b 2)` | ぶつからない | 書く番地が 0x1000 と 0x2000 で重ならない。ただしこの例は軽すぎて「並列にできる所」としては出ない(最小の重さの基準に満たない) |
| `a n = 4096 # n` と `b n = 4096 # n + 1` | ぶつかる | 「どちらも番地 0x1000 を使う」 |
| `w a v = a # v` を `(w 4096 1) + (w 8192 2)` | ぶつかる | 「どちらも番地が計算で決まる(\*)ので、重なるかもしれない」 |

最後の行がこの設計の要である。呼び出し側では番地が定数に見えても、関数の中では仮引数になっている。関数ごとに副作用を求める設計では、この場合を「分けられない」とするのが安全側である。速くできたかもしれない機会を手放す代わりに、答えをとり違えることはない。

## 順序を守るものと、変わりうるもの

デバイスの入出力(アドレス 0x9000000 以上)は、読み出しでも「書き込み」として扱う。デバイスは読むだけで状態が変わりうる(入力を一つ進める、時計を読む、など)し、順番に意味があるからである。同じデバイスを使う二つの式は、互いにぶつかると判定され、順番を守る。ツールはこの理由を「同じデバイスを使う(入出力は順番に意味がある)」と文で出す。

**守るもの、変わりうるもの。** ツールの前提は「言語の意味は変えない」である。引数は元々すべて評価されるので(どれかが `__` でも他の引数は評価される)、同時に評価しても値は同じ。変わりうるのは「エラーが複数あるとき、どれが先に報告されるか」だけと、ツールの説明文に明記されている。実際に `--par` で実装した側(第21章)でも、ノートはこれを「処理系の観測由来の決め」として記録している。両方が誤り・罠になるとき、先に出る方が直列とずれうる。罠はどれも同じ終わり方になり、Python では誤りの文面の順だけがずれうる。

複数の誤りが同時に起きたときにどれを先に報告すべきかを仕様が定めているかは、この章では確かめていない。確かめていない点は「実装だけの選択」として扱う。

**計画を確かめる試験。** `test_plan.py` は副作用の分類・番地の判定 6 種・波の順序・分割統治・投機・短絡・取り込み・出力形式を試し、ディレクトリの `*.sn` すべてで落ちないことも試す(ノートによると 26 件)。この章を書く際に走らせたところ、「全部通った」で終わった。

第8章のとおり、このツールは第10章の記憶や第21章の並列とコードを共有しない。同じ考え方を別の場所で実装しているだけなので、ここで「ぶつからない」と判定されても、実際の `--par` が同じ式を並列にするとは限らない。

## 限界

- 重さは構文木の節の数の概算で、実際にかかる時間ではない。「理想の速さ 4.0 倍」は仕事量を最長の道で割った見込みで、第21章の実機の値(並列で 1.95〜3.06 倍など)とは別のもの。
- 番地が計算で決まる式はすべて「ぶつかる」と見るので、実際は重ならないのに分けられない場面がある。これは意図した安全側である。
- この章の例は、判定を見るために小さく作ったプログラムです。実際のサンプルでの分布は測っていません。
- 2 つ目の例は、軽すぎて「並列にできる所」に出ませんでした。ぶつからないことと、並列にする得があることは別の判定です。

**仕様由来と実装の選択。** 引数を左から右へすべて評価するという意味を除いて、番地の集合・軽さの基準・デバイスを書き込みとみなす決めはすべて実装の選択です。仕様が定めているのは観測を変えないことで、並列にするかどうかは何も定めていません。
