# 第27章 仕様を言語弁護士の目で読む

## 仕様が何も言っていない所は、最適化の自由にしない

最適化は、仕様が許す範囲でしかしてはいけない。ここで言語弁護士の読み方と呼ぶのは、仕様の文言だけを根拠にして、「書いてある」「書いてない」「文書どうしが食い違う」を分けて読むことである。このプロジェクトでは、この三つに次の扱いを決めている。

| 読んだ結果 | 扱い |
| --- | --- |
| 仕様が決めている | そのとおりに実装する。実装が違うなら、直すのは実装の側 |
| 仕様が何も書いていない | 仕様に無いものは足さない。最適化で「どちらでもよい」と見なして速い方を選ばない |
| 仕様どうしが食い違う | どちらにも寄せない。記録して設計者に問う |

仕様は設計者が決めるもので、実装する側は仕様の起草に加わらない。仕様の欠陥は「設計者への問い」として文書に残し、設計者に渡す。この規律を守ると、最適化を今してしまいたくなる理由が、設計者の答えが出たときに観測を壊す形を取らなくなる(第28章)。

**「誰の文言か」を先に見る。** このリポジトリの `documents/` は Sign そのものを記述して最優先である。alpha1 の仕様文書はその下にあり、文書が遅れているだけの食い違いもありうる。したがって食い違いを見つけたときは、どちらが新しいか(git の履歴の日付)、どちらが設計者自身の文言かを確かめ、「遅れの可能性」をメモに添える。ただし新しい方を選んで実装に反映することはしない。選ぶのは設計者だからである。

## 食い違う 6 件を、どちらも実装せずに残す

設計者への問い 1 枚(`designer_questions_one_page_2026-11-23.md`)は、仕様を全問読み直して残った「文書どうしの食い違い」6 件を並べたものである。どちらも設計者の文言なので、実装の側では直せないと書いている。各問いの下に「(a)(b) のどちらか、または別の答え」を置き、答えが出れば実装・試験・教材を合わせるという約束である。

| 番号 | 問い | 食い違う二つ | 実装の今 |
| --- | --- | --- | --- |
| A3 | `9223372036854775807 + 2` はどうなるか | 罠で止まる(integer\_overflow.md など) / `!_`(value\_spec V5) | `--strict` は `!_` と information。コンパイラは罠で止まるまま |
| A5 | 同じ枚に同名の関数を 2 つ書く | 止めず、2 つ目を使わず information 1 件(先勝ち) / 断る(P2) | `--strict` は先勝ち(値 1) |
| B1 | `Point : x y ? [ x : x  y : y ]` のようなコンストラクタ | 通る(type\_system.md の例) / name-cycle で断る(R133・P2) | `--strict` は name-cycle |
| C4 | `z : ? 5`(仮引数の無い関数) | 通る(type\_system.md) / 読む段で止める(R119) | 止める(pointfree-tree-notation) |
| D1 | 実行時に大きさの決まるデータの確保 | 確保がある(memory\_management.md など) / 前置 `#` は export の印だけ | 前置 `#` だけを読む |
| D4 | `##x : 5`・`###x : 5` | export の印 / 確保の種類 | `##`・`###` は「未対応の前置演算子」で断る |

この表で大事なのは、実装の今の動きを「正しい」と主張していないことだ。列を並べると、実装はどちらかの文言に寄せたり、間を取ったりしている。これは「今はこう動く」という記録であり、設計者の答えが出たら変える。

**記録の残し方。** 問いは、1 件ごとに「例・一方の文書と日付・他方の文書と日付・実装の今・答えの選択肢」を一枚にまとめる。読むことと選ぶことを分け、選択肢を設計者が選べる形にする。実装だけで決められない「書かれていない番地の読み」(H1)も、同じ頁の末尾に「仕様に決めがない」として並べている(評価器は `__`、機械語は 0)。

## 限界

- 帰納の表は、設計者への問い 1 枚(2026-11-23)を読んで要約したものです。各文書の行番号や文言はここで再確認していません。仕様リポジトリは HEAD 0114ac8a 時点の読みです。
- 6 件の答えはまだ届いていません。答えが出たときにこの章の「実装の今」の列は古くなります。
- 「文書が遅れている」の見分けは、日付の新しさでは確定できません。ここでは「遅れの可能性」を添えるだけです。
- この規律はこのプロジェクトの選択で、一般の言語処理系にも当てはまるとは限りません。仕様の起草者と実装者が同じ人なら、直す側は違うかもしれません。

**仕様由来と実装の選択。** 「仕様が何も書いていない所を足さない」「食い違いは設計者に問う」という規律は、このプロジェクトの進め方です。表の「実装の今」の列は実装だけの選択で、仕様が定めた結果ではありません。
