# 第7章 速い道 run\_pure

評価器の最適化で最も効いたのは、整数だけの純粋な関数を木の走査ではなく翻訳して走らせる「速い道」で、仕様とは関係のない処理系だけの選択である。

## 何をするか、どこまで対象にするか

対象は、仮引数が名前だけ(既定値なし・可変長でない)で、本体が「条件 : 式」の行と既定の行だけ(または式 1 つ)の関数だ。条件は整数の比べと、それを `&` `|` でつないだ物と括りに限る。この範囲を Python のコードに翻訳して走らせる。「増やす前に、狭くて確実な範囲で答えを守る」という立て方である。

守りは五つ。

1. `&` `|` は左で決まれば右を見ない(普通の道と同じ結果)。
2. 0 で割るなど決まらないことがあれば捨てて、普通の道を最初からやり直す(この範囲に副作用がないので結果は変わらない)。
3. `/` `%` は被除数の符号で 0 へ丸める規則を再現する。
4. 負のシフト・10 万を超えるシフトは決めずに普通の道へ任せる。
5. 呼ぶたびに「名前が同じ関数・同じ環境を指すか」「外の整数が同じ値か」を見直す。

既定の道だけで、`--strict` では使わない。`SIGN_NO_PURE=1` で切って同じプログラムを比べられる。

## 実測

このコンテナ(Pi ではない普通の Linux)で、同じプログラムを既定の道と `SIGN_NO_PURE=1` で走らせた。`fib 24` の答えはどちらも 46368。

| 設定 | 時間 |
| --- | --- |
| 既定(速い道。メモ化を含む) | 0.030 秒 |
| `SIGN_NO_PURE=1`(普通の道) | 1.765 秒 |

約 60 倍だが、これは速い道の翻訳だけの効果ではない。既定にはメモ化(整数の引数だけ、上限 20 万件)が入っていて、`fib` のような二重再帰では呼び出しの大半が表引きになる。翻訳とメモ化を分けた測定はしていないので、内訳は言えない。

実装ノートには `fib 22` が約 1.0 秒から約 0.1 秒、`fib 24` が約 2.7 秒から 0.11 秒という別の機械での数字がある。機械が違えば絶対値は違うが、桁が一つ下がる点は同じだった。

注意が二つある。

- 速くなるのは対象の狭い範囲だけで、文字列・リスト・デバイスを使うプログラム全体は速くならない。
- 最初に試した書き方は速い道に入らず、速くならなかった。`n ?` と「条件 : 式」の行で書いて初めて効いた。速さは書き方に左右される。

## 観測の違い: 深い再帰

速い道は答えを変えないことを目指して作ったが、実装ノートが認める違いが一つある。深い非末尾再帰で、速い道は答えを返し、普通の道は失敗する。

```
d : n ?
	n < 1 : 0
	1 + (d (n - 1))
d 60000
```

既定では 60000 と出る。`SIGN_NO_PURE=1` では「再帰が深すぎます(スタックの大きさが足りません)」という誤りになる。

分類すると、これは仕様の違いではなく実装の限界である。普通の道が何段まで再帰できるかは、仕様に書かれていない。だから「普通の道が失敗する」ことは仕様の答えではなく、「速い道が答える」ことも仕様に反しない。仕様が定めない範囲で、実装の二つの道が違う振る舞いをしているだけだ。

守りとしては、失敗の側(断る側)から答える側へ変わる向きの違いなので、誤答は生まない。逆向き(速い道が答えを変える)は `test_pure.py` が見張る。サンプル、端の値、相互再帰、局所関数、40 本のランダムな 2 関数プログラムで、両方の道の出力を比べている。
