# 第19章 共通部分式と不変量の持ち上げ

## 枝をまたぐ同じ式(`share_exprs`)

関数の本体で、同じ算術式が行をまたいで何度も現れることがある。次は、試験 `test_share.py` の例である。

```
g : a b ?
	a > b : 0 - 1
	((a + b) / 2) > 10 : (a + b) / 2
	((a + b) / 2) * 3
```

`(a + b) / 2` が 3 回現れる。普通に出すと、加算・割り算を 3 回計算する。`sign_fuse.share_exprs` は、この式を、**最初に評価する枝の条件の中で 1 回だけ**計算してスロットへ置き、あとの出現はスロットを読む。

やり方は「印をつける」である。

| 印 | つける場所 | コード生成ですること |
| --- | --- | --- |
| `sh` | 最初に評価する出現 | 式を評価し、x0 を関数の間生きるスロットへ置く |
| `ref` | あとの出現 | スロットを読む |

印は「長さ 4 の括り」で、型の解析は今までの括りと同じに見える。印を見るのは `FnGen.gen` の括りの所だけである。`ref` が `sh` より先に出てしまった場合(印が素通りされたとき)は、元の式をそのまま評価する。安全側に倒している。

最も大事な約束はこの一点である。**入口へ前倒ししない。** 式は元と同じ場所(その枝の条件)で初めて評価される。`g 9223372036854775000 1` は、先の枝 `a > b` で抜けるので `a + b` を評価しない。共通化してもここで罠にならない(`test_share.py` の試験にある)。入口で計算すると、抜けるケースにも溢れの罠が起きるからである(第16章)。

## ループの不変式(`lazy_invariants`)

仕組みは第16章で述べた。ここでは、「なぜ作ったか」と「なぜ対象を絞ったか」を実装ノートの記録で追う。

**なぜ作ったか。** `sign_opt` の命令ごとの移動は、罠になりうる命令(`mul`+`smulh` の溢れ検査、`adds`+`ccmp`+`b.vs`)を動かさない。そのため、変わらない積がループの中で毎回計算されていた。調べると、自己再帰する定義 85 個のうち、変わらない引数だけの算術式を持つのは 5 個だけであった(`font_text2`・`touches`・`lrow`・`ldrow`・`mk`)。

**対象の絞り込み**は次のとおり。

| 対象 | 理由(実装ノートの記録) |
| --- | --- |
| 乗除剰を含む式だけ | 足し引きだけの式は、スロットを読む `ldr`・`cmp`・`b` と命令数が同じで得が無い |
| 条件(cond)の中だけ | 行に着けば毎回評価される |
| 値の側(末尾呼びの実引数)は対象外 | 通るか分からず、2 回目以降が少ない。`font_text2` の `8 * sc` は静的に 79 → 89 命令と増えるので外した |
| `lazy` の中には `share_exprs` の印をつけない | メモのところで飛ばされうるため |

値の側を外したのは、「速くなるかどうかが実行時の回数しだい」だからである。無条件に有利とは言えない最適化は入れないという判断である。

## 試して外した・やめた案

実装ノートにある、実際にやめたものをまとめる。

| 案 | やめた理由 |
| --- | --- |
| 式をループの入口へ前倒し | 抜けるケースにも溢れの罠が起きる。罠の起きる時が変わる。 |
| 値の側(末尾呼びの実引数)の持ち上げ | ここの行の回数しだいで損得が逆になる(79 → 89 命令) |
| 「共通の値を余りのレジスタへ持ち越す」専用の仕組み | 作らなかった。スロットを `sign_opt` の割り付けが x19〜x28 に載せるので同じ効果が出る(`std_bs` では x22) |
| 器(リスト)の再利用 | 返値スロット 38 個のうち器を取って器を返すのは 8 個(すべて `suika_flat.sn` の固定 8 語のレコード更新)で、省けるのは確保と捨てだけ。利用者の回答で「レコードの分解(`scalarize_records`)」に切り替えた |

最後の「器の再利用」は、「試して外した」というより「測って違う案に切り替えた」例である。実装ノートは、同じ連なりの 3 段版を 1000 回回すと実行命令数が 232023 →(手で平らにした下限)70023 となり、効くのは再利用ではなく「連なりの途中のレコードを作らないこと」だと記録している。

## 実測と、仕様・実装の分け、限界

このコンテナで、上の `g`(`g 30 40`)を `sign_asm.generate` で出し、`share_exprs` を切るスイッチで比べた(コメントとディレクティブを除く粗い数え方)。

| 設定 | 命令行 | `sdiv` |
| --- | --- | --- |
| 共通化あり | 35 | 1 |
| 共通化なし | 47 | 3 |

`test_share.py`(9 例)と `test_hoist.py`(8 例)は、このコンテナで実行してどちらも「全部 ok」であった。この 2 つの試験は、処理系と共通化ありとなしの答えが同じで、罠の起きる時が変わらないことを見ている。

実装ノートの記録の数字も添える(自分で再現したのは上の表だけ)。

- `std_bs`: 86 → 67 命令、`sdiv` 5 → 1。
- 44 本のサンプルでは、共通化で変わったのは 2 本で、命令の合計が 32769 → 32744。先の枝をまたぐ式を使うプログラムが少ない。
- 不変式の持ち上げは、この 44 本では当たるものが無く、出力は変わらない(32744 → 32744)。作った機構の効きは、`lp i n k acc`(条件に `k * 3`)を 1000 回回すと実行命令数が 18022 → 16034(約 11% 減)。

仕様と実装の分けはこうなる。この章の最適化はどれも処理系だけの選択で、仕様は共通化について何も定めていない。守っているのは第16章の「罠の起きる時を変えない」である。溢れが罠になるか `!_` になるかは A3 で未決なので、どちらに転んでもこの章の最適化をやり直さないで済むかは確かめていない。

限界は三つ。

- 共通化の対象は、仮引数と整数の字面だけでできた算術式。仮引数が器(リスト)のとき、評価が確実に進まない位置(`&` `|` の右・入れ子の `cases`)の最初の出現には印をつけない。`cmp` の連なりや関数呼びの中の式も対象外(実装ノート)。
- 実機の速さは測っていない。ここの数字は命令数だけである。
- 上の表は最も効く形の 1 例で、一般的な効果の大きさは 44 本の記録のほうが近い(ごく小さい)。
